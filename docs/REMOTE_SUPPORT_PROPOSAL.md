# 用户授权远程诊断与协助方案（提案）

> 状态：草案，供产品决策使用；不代表已承诺实现。
>
> 适用范围：Windows 优先的客户电脑诊断与人工协助。
>
> 核心原则：客户始终知情、可见、可拒绝、可随时断开；“全部权限”不是默认能力。

## 1. 要解决的问题

希望客户安装一个 Autoto 支持端后，技术支持人员能够在客户明确授权的前提下：

1. 查看有限的设备健康信息和诊断报告；
2. 让 Autoto 在客户电脑上执行受控诊断任务；
3. 在客户同意时协助执行修复操作；
4. 后续可选地查看并操作客户桌面；
5. 让每次访问都有可见状态、时效、审计记录和撤销入口。

这不是隐藏控制、静默常驻或绕过 Windows 安全机制的功能。客户未授权、会话已结束或权限已撤销时，支持人员不能继续访问设备。

## 2. 结论与推荐范围

推荐先做“**有人在场的远程诊断**”，而不是直接做“全权限远程接管”。

首个可交付版本应满足：

- 仅支持 Windows；
- 客户主动启动支持端，且每次会话均显示连接状态；
- 支持人员只能访问被授权的 Autoto Agent、项目和诊断数据；
- 支持发送诊断任务、查看结果，并对单次操作进行审批；
- 不提供屏幕控制、键盘鼠标注入、后台常驻服务或管理员绕过；
- 会话默认短时有效，可由客户或支持人员立即撤销。

完成这一版本后，再根据真实支持需求决定是否投入桌面远控和管理员级操作。

## 3. 现有基础与缺口

### 3.1 已有基础

仓库中已存在两类可以复用的能力：

| 能力 | 当前状态 | 可复用价值 |
| --- | --- | --- |
| 远程访问 | 已实现 | 可通过 HTTPS 隧道访问 Autoto；本机所有者可显式开启 `full` 会话。 |
| 远程协作 / Peer Control | 底层实现处于 WIP | 一次性邀请、设备身份、公钥签名、短期会话令牌、授权范围、撤销和审计。 |
| Agent 工具审批 | 已实现 | 支持将高风险工具调用置为待审批状态，并记录审批结果。 |
| 审计与权限模式 | 已实现 | 可作为支持操作和授权变更的审计基础。 |
| 桌面壳 | 开发/内测可用 | 可作为客户侧支持端的外壳基础。 |

现有 Peer Control 当前只支持受限的项目/Agent 协作：查看脱敏快照、发送任务、一次性审批。每个授权目前最多为 `readOnly` 或 `acceptEdits`，并不等于操作整个 Windows 桌面。

### 3.2 尚未实现的部分

以下能力尚未产品化，也不能向客户承诺：

- 正式签名的 Windows 安装包、自动更新和卸载流程；
- 面向客户的“输入支持码—确认授权—一键断开”界面；
- 支持人员控制台与客户设备列表；
- 屏幕捕获、键盘鼠标控制、剪贴板或文件传输；
- Windows 服务、无人值守访问和管理员安装流程；
- UAC 提权的本地确认链路；
- 远程支持专用中继、带宽控制、会话录像和保留策略；
- 面向客户支持场景的端到端测试、滥用防护和运维流程。

现有“远程访问 full 模式”适合设备所有者远程使用自己的 Autoto，不应直接作为面向客户的远程支持产品入口。

## 4. 目标用户体验

### 4.1 角色

- **客户 / 设备所有者**：安装、启动支持端，决定允许哪些能力，随时结束会话。
- **支持人员 / 控制端**：在自己的 Autoto 支持控制台中发起或接收支持会话。
- **支持服务**：只负责配对、身份验证、会话路由和审计；不应默认保存客户屏幕、文件或命令输出。

### 4.2 推荐会话流程

1. 支持人员创建一次性支持会话，生成短支持码或链接。
2. 客户从官方签名来源下载并启动支持端，输入支持码。
3. 支持端显示支持人员的名称、组织、设备指纹、申请能力、有效时间和隐私说明。
4. 客户逐项确认授权；未确认前，支持人员看不到客户数据。
5. 双方完成双向身份校验后建立短期会话。
6. 支持人员先获取有限的诊断快照，再发送诊断任务。
7. 每个高影响操作按风险要求再次确认；需要管理员权限时由客户在 Windows UAC 窗口本地确认。
8. 客户可在支持端点击“立即断开”；到期、撤销、关闭支持端或网络中断都会失效会话。
9. 会话结束后，客户看到操作摘要；支持端清除短期会话凭证。

### 4.3 客户侧必须可见的内容

支持端应持续显示：

- 当前是否有人连接；
- 连接的支持人员身份和指纹；
- 已允许的能力与到期时间；
- 最近执行的操作及结果摘要；
- “暂停”“断开”“撤销以后访问”的入口；
- 隐私提示：哪些数据会被读取、是否会保存、保存多久。

## 5. 权限模型

不要用一个“全部权限”开关覆盖所有行为。应使用短期、分级、可撤销的能力授权。

| 权限级别 | 示例能力 | 推荐首版状态 | 授权要求 |
| --- | --- | --- | --- |
| `observe` | 基础系统信息、Agent 状态、脱敏诊断日志 | 支持 | 客户一次确认，默认 30 分钟到期。 |
| `run_diagnostics` | 运行固定的只读诊断脚本、收集健康报告 | 支持 | 客户一次确认；脚本必须有白名单和可读说明。 |
| `approve_once` | 对某一次 Agent 工具调用批准或拒绝 | 支持 | 显示操作类型、风险和目标，再单次确认。 |
| `apply_fix` | 修改配置、安装依赖、重启指定服务 | 后续 | 每项操作再次确认，必须保留审计。 |
| `desktop_control` | 查看屏幕、鼠标键盘协助 | 后续 | 客户清楚确认、持续可见指示、默认有人在场。 |
| `elevated_action` | 需要管理员权限的操作 | 后续 | Windows 本地 UAC 确认；远端不能绕过或代替确认。 |
| `unattended_access` | 客户不在场时的访问 | 最后评估 | 单独产品能力，默认关闭，需要长期许可、设备绑定和强审计。 |

`full` 不应作为支持端对外的权限名称。即使以后提供完整协助，也必须由多个明确能力组合而成，并清楚告诉客户实际影响。

## 6. 建议架构

### 6.1 客户支持端

客户支持端是一个独立、签名的 Windows 应用，职责包括：

- 显示授权、连接和断开状态；
- 保存设备身份密钥和有限的本地配置；
- 主动向支持服务建立出站加密连接，不要求客户配置端口转发；
- 收集经允许的诊断信息；
- 将获准的任务交给本机 Autoto Runtime 执行；
- 对屏幕控制、管理员操作等高风险能力执行本地确认；
- 在会话结束时撤销短期凭证并停止数据流。

首版不安装 Windows 服务、不设置开机自启，也不在客户关闭窗口后继续运行。

### 6.2 支持人员控制台

支持人员控制台可以先作为 Autoto 内的一个模块，而不是单独新应用。它需要：

- 创建会话和查看会话状态；
- 显示客户已授予的能力，而不是假定拥有权限；
- 查看受限诊断快照和任务结果；
- 发送任务、请求操作、查看审批状态；
- 终止会话、撤销授权、导出受限审计摘要；
- 对敏感操作要求支持人员再次确认。

### 6.3 配对与控制平面

建议在现有 `internal/peercontrol` 的设备身份、邀请、挑战和短期 bearer 凭证基础上扩展：

- 每台设备都有独立密钥和可展示的指纹；
- 支持码只能兑换一次，默认有效期 10 分钟；
- 码本身不是长期登录凭证；
- 客户确认后才签发会话令牌；
- 每次权限变更都递增版本并使旧令牌失效；
- 支持端和控制端都应校验对方身份和会话范围；
- 所有访问均写入不可伪造的审计记录。

产品化版本通常需要一个专用的会合/中继服务，使客户只需输入短码即可连接。现有临时 Cloudflare 隧道可以用于原型验证，但不应承担完整客户支持平台的账户、设备和会话管理职责。

### 6.4 数据平面

诊断数据、Agent 消息和审批应通过范围受限的 API 传输。桌面图像和输入控制若以后实现，应与控制平面分离：

- 使用端到端加密的数据通道；
- 默认不录屏、不保存剪贴板、不自动上传文件；
- 网络受限时可走受控中继；
- 对帧率、带宽、文件大小和会话时长设置上限；
- 断连后立即停止输入和屏幕传输。

在决定桌面远控实现方式前，需要单独评估自研 WebRTC、集成成熟远控组件和使用 Windows 原生协议的安全、许可、维护与客户体验成本。不得为了快速实现而启用客户的公开 RDP、关闭防火墙或降低系统安全设置。

## 7. 诊断能力的首版边界

为了让首版真正可用，建议只提供可解释、可审计的固定诊断项，例如：

- Windows 版本、硬件、磁盘空间、内存和网络连通性摘要；
- Autoto Runtime、Agent、Provider 和日志健康状态；
- 指定应用的版本、服务状态和错误报告；
- 用户主动选择的日志文件或截图；
- 明确白名单内的只读 PowerShell / 命令行诊断。

以下操作不进入首版：

- 隐藏进程、静默持久化、规避安全软件；
- 扫描或上传所有个人文件；
- 自动读取密码、浏览器资料、密钥或令牌；
- 自动以管理员身份执行任意命令；
- 未经再次确认的安装、卸载、注册表修改或服务重启。

## 8. 安全、隐私与合规要求

### 8.1 安全要求

- 客户每次会话主动启动或明确恢复支持端；
- 支持码、邀请和短期会话令牌均不可重放；
- 设备身份采用独立密钥，私钥不离开设备；
- 支持人员账户需要强身份验证和最小角色权限；
- 所有权限、任务、审批、文件请求、连接和断开都写入审计；
- 令牌、权限、设备身份或支持人员账号变化时，现有会话立即失效；
- 远端输入、任务和文件路径在客户设备的最终执行点重新校验；
- 默认拒绝未知操作，审计写入失败时拒绝高风险授权；
- 客户可在本机删除设备绑定和所有持久授权。

### 8.2 隐私要求

- 收集前明确说明数据类别、用途、保存位置和保留期；
- 默认只传输完成诊断所需的最少数据；
- 日志、截图、文件和命令输出须脱敏、限长、加密传输；
- 禁止将客户数据用于训练、分析或营销，除非取得单独同意；
- 会话录像、文件传输和剪贴板同步必须独立开关；
- 支持结束后提供客户可读的会话摘要和删除请求路径。

### 8.3 管理员权限要求

管理员权限是 Windows 本机授权，不是远端角色可以授予的能力。设计必须保证：

1. 客户本机看到真实的 UAC 提示；
2. 远端支持人员不能代替客户点击或绕过 UAC；
3. 提权仅覆盖当前明确操作，不自动转为长期管理员会话；
4. 所有提权请求记录操作目的、时间和结果；
5. 无法获得本机确认时，应提供手工操作说明而非尝试绕过。

## 9. 交付阶段

### 阶段 0：产品决策与安全评审

产出本提案确认版、威胁模型、隐私告知文案、支持人员角色规则和客户授权界面原型。

### 阶段 1：有人在场的诊断 MVP（推荐先做）

- 签名的 Windows 支持端原型；
- 一次性支持码和双向身份展示；
- `observe`、`run_diagnostics`、`approve_once`；
- 支持任务发送、诊断报告和会话审计；
- 客户一键断开、到期失效和撤销；
- 不含桌面远控、文件传输或管理员操作。

验收标准：客户能在无端口转发的普通网络中完成一次支持会话，并能清楚看到连接者、授权范围、剩余时间与断开结果。

### 阶段 2：受控修复

- 固定修复动作的请求与二次确认；
- 每个操作的前置检查、预期影响和回滚说明；
- Windows UAC 本地确认；
- 更完整的审计摘要和支持人员角色控制。

验收标准：任何可能改变系统的操作均可在客户侧看见、拒绝、追溯，并能在失败时提供恢复路径。

### 阶段 3：有人在场的桌面协助

- 客户授权后的屏幕查看；
- 可选鼠标键盘控制；
- 持续连接提示、暂停和断开；
- 带宽、剪贴板、文件传输和录制的独立开关。

验收标准：断开、锁屏、授权变化或网络中断后，远端立即失去画面与输入能力。

### 阶段 4：无人值守访问（仅在确有需求时）

这是独立的高风险产品线，不应自动从前述阶段延伸。需要额外完成设备所有者长期授权、企业账号/角色、设备清单、强认证、定期重新确认、异常访问告警、审计保留和合规评审。

## 10. 需要在开工前确认的决策

1. 首版是否只服务 Windows，还是要兼容 macOS/Linux？
2. 客户是否必须全程在场？推荐“是”。
3. 首版是否仅做诊断，还是包含受控修复？推荐先仅诊断。
4. 是否需要屏幕控制？推荐作为阶段 3 的独立决策。
5. 支持人员是否只限内部团队？推荐是，并使用组织账号与强认证。
6. 客户数据是否允许离开设备保存？推荐默认不保存，只保留脱敏审计摘要。
7. 是否需要无人值守？推荐暂不做。
8. 采用自建中继、受控云服务，还是先以现有临时隧道做原型？推荐原型使用现有基础，产品版再建设专用会合服务。

## 11. 对现有代码的预期影响

如果决定实施，主要会涉及：

- `internal/peercontrol`：扩展支持码、能力声明、会话失效和双向身份验证；
- `internal/server/remote_collaboration.go` 与 `remote_peer_api.go`：新增支持会话、诊断和审计 API；
- `internal/db`：支持会话、授权、设备、审计与保留策略的数据模型和迁移；
- `internal/desktop` / `cmd/autoto-desktop`：客户授权、连接状态、断开和本地确认界面；
- 前端模块：支持人员控制台和客户可读的会话摘要；
- 发布流程：Windows 安装包、代码签名、更新、卸载和安全响应流程；
- `SECURITY.md`、`README.md`、测试套件：更新边界、威胁模型和端到端验证。

这些工作会触及远程访问和权限边界，实施前应先通过独立设计评审，而不是直接从现有 `full` 远程模式扩展。

## 12. 建议的下一步

先确认本提案中的首版范围。若认可“Windows + 有人在场 + 诊断优先”的方向，下一步可以拆出一个独立的阶段 1 实施计划：界面原型、协议调整、数据模型、安装包、测试和安全验收标准分别评审。
